# API Map

## Settings, access control, and database recovery

Apply `node --env-file=.env scripts/apply-settings-access.mjs` to create `user_module_permission`. `server/middleware/module-access.ts` checks the current `user` role/status and per-user module rights on every `/api/dashboard`, `/api/employees`, `/api/organization`, `/api/attendance`, `/api/rates`, `/api/deductions-loans`, and `/api/payroll` request. GET/HEAD needs View, writes need Edit. The DTR-record GET skips its automatic synchronization writes for view-only users. Admin bypasses module limits; existing stricter approval/finalization role checks remain. Default non-admin rights are View for all modules and Edit for Supervisor/Encoder, with Viewer read-only. Billing and Reports currently have no protected backend routes. Settings account access is available to all signed-in users; its user controls and database actions require a current Admin role. The dashboard navigation hides modules without View access, and the API rejects direct requests independently of the UI.

## Payroll processing, finalization, and cancellation

Apply `node --env-file=.env scripts/apply-payroll-processing-review.mjs`, `node --env-file=.env scripts/apply-payroll-processing-finalization.mjs`, `node --env-file=.env scripts/apply-payroll-processing-cancellation.mjs`, and `node --env-file=.env scripts/apply-recurring-payroll-deductions.mjs` in order before using these endpoints. The cancellation migration lets `payroll_processing_posting` preserve cancelled mappings while allowing a new active mapping after recomputation; it adds Cancelled payroll/review and workflow statuses plus the prior adjustment status field. The recurring migration adds fixed-amount employee plans without declining balances and per-cutoff skip audit rows. `payroll_processing_review` retains Pending, Approved (finalized), Rejected, or Cancelled and a frozen breakdown. Workflow events retain actor name, role, department, reason, DTR status transition, and time.

`app/pages/payroll/processing/index.vue` lists computed, finalized, returned, and cancelled site DTRs. The detail modal shows attendance earnings/time deductions, eligible active loan/deduction installments, agency-position contribution amounts, Approved/Ready for Payroll prior-period adjustments, and saved BTR coverage totals. In a newly computed payroll review, active BTR hours reduce the REST employee's regular hours on each covered date and increase the reliever's Regular earnings at the rate effective on that date; source DTR attendance is unchanged. Coverage exceeding the REST employee's available regular hours, an unenrolled REST employee or reliever, or a reliever without an effective regular rate blocks finalization. Each attendance date uses its effective payroll rate version. Installments and agency-position contributions are charged only to an employee's fixed-site DTR (`attendance_dtr_employee.IsPermanentSite = 1` and not Reliever), once per cutoff; a reliever-only DTR has none. `PauseStartDate` and `ResumeDate` determine whether an employee plan is skipped for a cutoff. Draft/For Approval adjustments, missing/non-effective rates, and unsupported combined premiums block finalization. A configured payroll-rate Allowance is a flat earning paid once per employee per cutoff when the employee has payable attendance or BTR coverage with an effective rate. The fixed-site DTR receives it when that site has payable work; otherwise one reliever-site DTR receives it. The amount uses the effective rate on the latest payable work date at the selected site and is included in gross and net preview. Statutory contribution formulas are not calculated automatically; the contribution amount comes from the agency-position plan. Finalization saves payroll and account transactions but does not release payslips or pay. Cancel finalization is available for an Approved, unreleased payroll; it voids payroll and receipts, restores unchanged account balances, reopens applied adjustments, retains audit records, and returns the DTR to Draft for correction and recomputation. It refuses cancellation when a receipt, balance, adjustment, or payroll has since changed. Cancelled and other completed reviews retain their saved snapshots until a Draft DTR is computed again.

Automatic-break handling: `GET /api/payroll/processing` and finalization through `POST /api/payroll/processing/:id` read the source DTR site's active `site_policy.AutoBreakEnabled`. When on, saved DTR paid hours already exclude the break, so `BreakHours` produces no additional monetary deduction. Late and undertime deductions, loan installments, and contributions keep their existing rules. When off (or no active policy), the configured manual `BreakHours * BreakDeduction` behavior remains. `POST /api/payroll/adjustments` reads the original DTR site's policy and applies the same rule when creating saved-attendance adjustment lines, independently of the target site's policy. No attendance hours, existing adjustment lines, finalized payroll, payslips, or frozen review snapshots are rewritten. To correct an unreleased finalized payroll, use Cancel finalization, recompute the DTR, review, and finalize again.

Existing `Approved` review rows from before this migration are treated as pending unless a `payroll_processing_posting` mapping exists; they can be recalculated and finalized without mistaking an old review for posted payroll.

## Payroll history

Payroll History is a read-only ledger of DTR site cutoffs with posted payroll. Current totals count only Active postings whose payroll is Approved or Released. Cancelled postings remain visible separately in the detail view and never increase current gross, deductions, net, or employee counts. A cutoff finalized again after cancellation shows both its current employee rows and older cancelled rows, with finalize/cancel workflow events and actor/reason/time. Returned or pending reviews without posted payroll are not listed.

## Employee payslips

### Payslip List by Site

Payroll navigation includes **Payslip List by Site** (`payslip-sites` dashboard view; direct page `/payroll/payslip-sites`). It lists one entry per finalized processing DTR, preserving the DTR's site, agency and cutoff rather than combining agencies that share a physical site. Only active `payroll_processing_posting` mappings to Approved/Released payroll qualify; cancelled payroll is excluded. Historical inactive agencies/sites remain visible in finalized history. Finalization makes the entry available but does not automatically publish it.

Database compatibility: the shared finalized-group query converts the DTR/deployment assignment expression to `utf8mb4_unicode_ci` before comparing it with `Reliever`. Existing installations can have `attendance_dtr_employee.AttendanceType` in `utf8mb4_unicode_ci` and legacy `employee_deployment.DeploymentType` in `utf8mb4_general_ci`; comparing their unnormalized `COALESCE` result caused MariaDB error 1267 in both list endpoints. This is query-only normalization and does not migrate or rewrite payroll records. The site regression fixture deliberately uses these mixed collations.

Both staff list endpoints share `finalizedPayslipCte` source validation: a Posted publication counts only when all its source IDs still exactly match the current finalized employee/cutoff/assignment group. Added, cancelled or reassigned sources invalidate the old posted status consistently across both lists. `readPayslipProfiles` batches roster reads by employee and cutoff, avoiding a separate query set per employee. Individual `GET /api/payroll/payslips?employeeId=...` additionally returns `canPost`. The reused Payslip profile can be embedded with an employee prop; it retains individual posting, portal status, and existing Admin/Supervisor-only account activation/deactivation/recovery controls through the unchanged account endpoints. Closing that profile refreshes the site roster and list. Both workspaces refresh after navigation reactivation.

Regular employee payslips continue combining all regular sources in a cutoff; relievers continue receiving separate site payslips. Site review displays site-only totals alongside the full payslip's source sites. Bulk actions publish or withdraw the entire combined payslip, so other contributing site rows also reflect its status. The employee portal still exposes only the authenticated employee's currently valid Posted snapshots. No migration or separate publication store is required.

`requireEmployeeSession` lives in `server/utils/employeePortalAuth.ts`, separate from staff `requireSession`. The `pbs_employee_session` cookie is HttpOnly, SameSite Strict, Secure in production, expires in 12 hours, and contains an opaque random token whose hash alone is stored in the session table. Every request rechecks current account and employee availability. It never creates a staff JWT or `pbs_session` cookie. Mutations require JSON and reject a mismatched Origin. Content-Length requests above 16 KiB are rejected. Database-backed fixed-window limits use the socket address (not untrusted forwarding headers) and hashed login identifiers; default signup/recovery limit is five per 15 minutes and login limit 15. Old attempt buckets expire after 24 hours; expired sessions are cleaned on session creation. For proxy/public hosting, apply trusted proxy handling and web-server request-size limits appropriate to that deployment.

Numeric recovery uses `server/utils/employeePortalRecovery.ts` and the existing account/attempt tables; no schema migration is required. Previously issued hexadecimal codes must be replaced using **Issue recovery code**; they are no longer accepted by the numeric form/API. Staff code display uses selectable, spaced digits and explains expiry, one use, attempts and account email. The public form requires login email and uses a numeric keyboard with a text input so leading zeroes survive. Tests use temporary tables to cover expiry, other-account isolation, replacement, one use, invalidation after five guesses across IPs/windows, reissue after invalidation, and a leading-zero code. The mobile browser fixture verifies numeric-only entry and the recovery request body. Do not log plaintext recovery codes or include them in audit events.

Passwords follow the existing 12-character letter/number policy and reject more than 72 UTF-8 bytes to avoid bcrypt truncation. Public errors do not reveal employee names, government numbers, or matched document records. Audit records contain accepted notice text/version and server timestamps but **are not proof of the person's identity or a waiver of privacy obligations**. ## Payroll adjustments

**Manual amount adjustments:** Apply `node --env-file=.env scripts/apply-payroll-adjustment-amounts.mjs` to an existing installation (the main `apply-payroll-adjustments.mjs` installer also calls it). ### Government ID duplicate protection

Run `node --env-file=.env scripts/apply-government-id-uniqueness.mjs` after the attachment migration. The idempotent installer uses the fixed definitions in `database/government-id-uniqueness.mjs`. It checks existing IDs and private scans for duplicates before changing the schema, creates a safety SQL backup, adds generated `GovernmentTypeKey`/`GovernmentNumberKey` columns and a nullable `AttachmentSHA256`, fingerprints existing scan bytes, then installs unique indexes `uq_government_identity` and `uq_government_scan`. It never deletes or merges existing employee/ID records. Existing conflicts or missing files stop installation for review; they are not silently removed. Generated expressions explicitly use one collation to support the existing mixed-collation MariaDB schema. Re-running completes an interrupted index installation.

POST/PUT and DELETE coordinate with installation using the same connection-scoped `pbsystem:government-id-write` advisory lock; normal writes still use transactions and a final database unique constraint. ID comparisons cover all employees and agencies, including inactive employee records. Standard aliases map to one ID type, spaces/dashes are ignored, letters are compared case-insensitively, leading zeroes and Driver's License prefixes are retained. TIN compares its first nine digits so branch-code formatting cannot assign the same base TIN to another employee. Custom ID names form separate namespaces; an identical numeral in unrelated ID types is allowed. A same-record edit is excluded from duplicate lookups. User-supplied hash/key columns are ignored.

The server hashes validated attachment bytes using SHA-256 before saving, so renaming a file cannot bypass exact-scan checks. Hashes remain private (not returned in document lists). A new/replacement attachment updates its hash in the transaction; removing a scan clears its hash. Number and scan conflicts return 409 with the existing employee reference (or an instruction to edit this employee's existing record), keep the form open, and do not create/replace stored files. Unique-index conflicts also return a generic 409 rather than raw database errors. An altered/resized/re-photographed scan has different bytes; duplicate-number checks handle it when OCR/manual entry supplies its existing number. Unreadable or incorrect OCR does not prove a person's identity.

Tests use connection-local temporary copies of the real schema plus synthetic files: cross-employee create/update conflicts, aliases/formatting, TIN branch variants, duplicate bytes under another filename/type, self-edit, direct database constraint enforcement, rollback/file preservation, early OCR rejection, post-recognition rejection, and disabled form submission on duplicate scans.
